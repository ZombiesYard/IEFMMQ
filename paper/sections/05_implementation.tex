\chapter{Reproducibility and Artifact Provenance}\label{ch:implementation}

The preceding methods chapters define the evidence-grounded tutoring loop, the
visual-fact adaptation protocol, and the formative Quest~3 pilot. This chapter
links those methods to the artifacts used to support the reported claims. It
defines the artifact classes, authority rules, and reproducibility limits that
make the results auditable. Implementation details are included where they
determine claim provenance, constrain model authority, or define how a reported
result can be checked.

\section{Artifact and Claim Boundaries}\label{sec:impl-boundaries}

The research artifact separates procedural knowledge, runtime logic, external
systems, and exported evidence. The procedure pack stores the F/A-18C Lot~20
cold-start steps, gate definitions, telemetry bindings, UI targets, and
visual-fact bindings. The runtime loads those declarations and produces
evidence packets, model prompts, validation decisions, overlay actions, and
event logs. DCS World, the external telemetry interface, the Quest~3 display path, model servers, and
screenshot capture are external systems.

This boundary prevents evidence transfer across claims. Generated model text is
not treated as a research observation by itself. It becomes usable evidence only
after it passes the appropriate schema, mapping, harness, benchmark, or manual
review step. The thesis therefore reports three artifact classes:

\begin{itemize}
\item \textbf{Declarative configuration:} procedure steps, telemetry maps,
visual-fact ontologies, UI targets, source-policy rules, and replay-suite
definitions.
\item \textbf{Generated evidence:} JSONL event logs, trial summaries, help-cycle
tables, benchmark predictions, benchmark metrics, and quality-gate reports.
\item \textbf{Human-reviewed evidence:} reviewed visual labels, manual step
coding overrides, questionnaire records after exclusion rules, and anonymised
free-text comments.
\end{itemize}

Each research question uses a different unit of evidence. RQ1 is inspected at
help-cycle granularity: trigger context, available evidence, model response,
validation decision, and overlay result. RQ2 is inspected at image and fact
granularity: reviewed label vector, prediction, parse status, and per-fact
error. RQ3 is inspected at participant and step granularity: trial summary,
manual coding, questionnaire row, and comment. A VLM benchmark number is not
used as participant evidence; a participant completion row is not used as proof
that every model response was correct.

\section{RQ-Level Provenance}\label{sec:impl-provenance}

\paragraph{RQ1: tutoring-loop auditability.}
The runtime writes append-only events and analysis exports rather than only
rendering transient headset guidance. A help cycle records trigger context,
telemetry snapshot, active step, gate diagnostics, retrieved snippets, visual
facts when available, prompt-construction metadata, response status, validation
result, overlay execution status, and fallback or repair metadata. The same
format supports replay: recorded telemetry streams can be passed through the
same telemetry map, procedure gates, source policy, and harness contracts used
by the live runtime. This is the artifact basis for the RQ1 claim that the
tutor is auditable.

\paragraph{RQ2: visual-fact benchmark traceability.}
All VLM metrics reported in Chapter~\ref{ch:evaluation} are copied from local
benchmark artifacts such as \texttt{metrics\_base.json},
\texttt{metrics\_lora.json}, \texttt{benchmark\_summary.json}, and per-fact
score files. The selected benchmark figures in the main text are copied from
the same report assets. The evidence chain is: cockpit image capture, human
label review, bilingual supervised fine-tuning row generation, LoRA training,
and independent holdout benchmarking with a fixed prompt, schema, generation
settings, and metric computation. Training-runtime and loss values are treated
as training-report provenance; the reported claims rely on the benchmark JSON and
reviewed-label artifacts.

\paragraph{RQ3: pilot data authority.}
Each participant trial is represented by a trial directory containing event
logs, a trial summary, step coding, action timeline, help-cycle table, session
metadata, and quality-gate report. Post-trial forms provide experience,
confidence, NASA-TLX dimensions, tutor-specific ratings where applicable,
general custom user ratings, and free-text comments. The analysis applies
three authority rules: P08 uses manual step coding when automatic
reconstruction disagrees; P02 keeps task-log metrics but excludes
questionnaire-derived values because of an internal participant-id mismatch;
and P09 is analysed as an independent participant after the participant
correction recorded in the metadata.

These provenance rules keep the pilot claim bounded. The pilot can describe
observed completion, coded errors, raw workload ratings, custom post-trial
ratings, comments, and tutor-interaction counts in a small formative sample.
It cannot
support statistical significance, causal learning effects, retention, transfer,
workload reduction, or faster-completion claims.

\section{Reproducibility Limits}\label{sec:impl-repro-limits}

The repository supports local inspection of the manuscript, exported analysis
tables, replay fixtures, benchmark summaries, and selected figures. Full
experimental reruns require external state: DCS World, the F/A-18C module,
external telemetry interface integration, a Quest~3 setup, model-serving access, GPU resources for
VLM adaptation, and the conditions of the formative participant sessions.
This thesis therefore distinguishes \emph{artifact reproducibility} from
\emph{full experimental rerun reproducibility}. The former is the claim made
here: reported results are traceable to stored artifacts and can be checked for
internal consistency. The latter requires rebuilding the simulator, hardware,
model, and participant context.

This distinction also explains the role of the original proposal. The proposal
is useful for understanding the motivating VR scenario and later scope
evolution, but it is not used as evidence for the final system results. Claims
in the results chapter are tied to the implemented procedure pack, runtime
exports, benchmark JSON, reviewed labels, and pilot artifacts rather than to
the proposed design alone.
