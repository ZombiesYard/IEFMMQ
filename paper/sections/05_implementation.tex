\chapter{Implementation}\label{ch:implementation}

This chapter describes the concrete implementation of the SimTutor system whose design was presented in Chapter~\ref{ch:system-design}.
It covers the technology stack, the core domain modules, the telemetry and DCS integration pipeline, the structured help generation subsystem, the VLM visual fact extraction runtime, the replay and logging infrastructure, and the CLI and live runtime entrypoints.
Methodology-level details---the VLM adaptation protocol, dataset curation, and benchmark design---appear in Chapter~\ref{ch:methodology}.

\section{Technology Stack}\label{sec:impl-stack}
% Evidence: pyproject.toml, model_access.md

The SimTutor Python codebase is managed with Poetry\footnote{Version 0.1.0, declared in \texttt{pyproject.toml} under the package name \texttt{simtutor-core}.} and requires Python 3.10 or later.
Core library dependencies are kept minimal: \texttt{httpx} (v0.28+) for HTTP client functionality, \texttt{PyYAML} (v6+) for all declarative configuration, \texttt{jsonschema} (v4.23+) for Draft 2020-12 JSON Schema validation of model outputs and telemetry frames, and \texttt{Pillow} (v12+) for image handling in the VLM pipeline.
Testing relies on \texttt{pytest} (v7.4+) and \texttt{pytest-cov} (v5.0+) with branch coverage enabled.
% Evidence: pyproject.toml lines 21-29

The DCS Lua-side integration comprises five scripts deployed to the DCS \texttt{Saved Games} directory:
\texttt{Export.lua} bootstraps the DCS-BIOS export protocol;
\texttt{VRHilite.lua} and \texttt{SimTutorHighlight.lua} listen on UDP sockets for highlight, clear, and pulse commands and render them as cockpit overlays via \texttt{net.dostring\_in};
\texttt{SimTutor.lua} and its companion \texttt{SimTutor Function.lua} handle composite-panel screenshot capture and the DCS-BIOS hub integration.
% Evidence: DCS/Scripts/Export.lua, DCS/Scripts/Hooks/VRHilite.lua,
%           DCS/Scripts/SimTutor/SimTutor.lua

Model serving is provider-agnostic.
The primary path uses an OpenAI-compatible API endpoint (intended for vLLM, llama.cpp, or TGI servers), configured via the environment variable \texttt{SIMTUTOR\_MODEL\_PROVIDER=openai\_compat} together with a base URL and API key.
An Ollama fallback (\texttt{SIMTUTOR\_MODEL\_PROVIDER=ollama}) provides local compatibility without an API key.
A deterministic stub (\texttt{SIMTUTOR\_MODEL\_PROVIDER=stub}) returns fixed responses for testing without any external model service.
Multimodal support is enabled by setting \texttt{SIMTUTOR\_MODEL\_ENABLE\_MULTIMODAL=1}, which causes the OpenAI-compatible adapter to include base64-encoded images in the request payload.
% Evidence: model_access.md §§1-5

LoRA fine-tuning of vision-language models uses the Unsloth library with PEFT and TRL, targeting Qwen3.5-9B-Base as the primary backbone and Gemma-4-31B as a supplementary line.
Pre-labeling and human review of vision fact annotations are conducted in Label Studio.
% Evidence: tools/train_qwen35_vlm_unsloth.py, tools/train_gemma4_vlm_unsloth.py,
%           tools/generate_vlm_prelabels.py

\section{Core Domain Layer}\label{sec:impl-core}
% Evidence: core/procedure.py, core/gating.py, core/scoring.py,
%           core/vision_facts.py, core/llm_schema.py, core/types.py,
%           core/types_v2.py, core/event_store.py, core/vars.py,
%           core/overlay.py, core/knowledge.py
% Claims: C-ARCH-01, C-PROC-01

The core layer implements all domain logic that is independent of any particular simulator, model provider, or external service.
It is organised into approximately fifteen modules, each with a narrow responsibility.

\subsection{Procedure Engine}

The \texttt{ProcedureEngine} class in \texttt{core/procedure.py} implements the step state machine described in Section~\ref{sec:design-procedure}.
Each step is represented by a \texttt{StepState} dataclass holding a step identifier and one of four statuses defined in the \texttt{StepStatus} enumeration: \texttt{PENDING}, \texttt{ACTIVE}, \texttt{DONE}, or \texttt{BLOCKED}.
The engine enforces that at most one step is \texttt{ACTIVE} at any time.
Five operations are exposed: \texttt{activate\_next} advances the next \texttt{PENDING} step to \texttt{ACTIVE}; \texttt{complete\_active} transitions the active step to \texttt{DONE}; \texttt{block\_active} marks it \texttt{BLOCKED}; \texttt{rewind} returns a completed step to \texttt{ACTIVE}; and \texttt{check\_timeout} tests whether the active step has exceeded a configurable wall-clock limit.
All state transitions emit internal event records with ISO-8601 timestamps and optional reason strings; these events are later propagated to the JSONL event store.
% Evidence: core/procedure.py lines 10-60

\subsection{Gating Rule Engine}

The gating engine in \texttt{core/gating.py} evaluates precondition and completion gates expressed in a small domain-specific language.
Four operators are implemented: \texttt{var\_gte} (telemetry value threshold), \texttt{arg\_in\_range} (numeric interval membership), \texttt{flag\_true} (boolean flag with string coercion), and \texttt{time\_since} (elapsed wall-clock time since a tagged event).
Each rule returns a \texttt{RuleResult} dataclass carrying a boolean status, a failure path in dot-notation, and a human-readable reason.
The evaluator includes explicit unknown-value handling: the sentinel strings \texttt{"unknown"}, \texttt{"unk"}, \texttt{"missing"}, \texttt{"n/a"}, and \texttt{"na"} cause rule failure with a diagnostic message rather than silent treatment as \texttt{False}.
Rules short-circuit on first failure; the index and reason of the first unsatisfied rule feed into the deterministic step inference logic.
% Evidence: core/gating.py lines 1-80

\subsection{Scoring Engine}

The scoring module in \texttt{core/scoring.py} implements a simple event-log scorer following the error taxonomy defined in the procedure pack.
It counts two classes of error: omissions (\texttt{OM}), defined as canonical steps up to the maximum observed step that were never completed, and state violations (\texttt{SV}), identified by \texttt{"state\_violation"} tags in observation payloads.
A critical-step multiplier is applied to omissions of steps marked \texttt{critical} in the step registry.
Three additional categories (\texttt{CO}, \texttt{OR}, \texttt{PA}) have their counters and base weights defined in the taxonomy but default to zero in the current v1 scoring implementation.
The total error score is computed as a ceiling-rounded weighted sum.
% Evidence: core/scoring.py lines 1-101

\subsection{Vision Fact Ontology and State Management}

The vision facts module in \texttt{core/vision\_facts.py} centralises the 13-fact v2 ontology as the \texttt{VISION\_FACT\_IDS} tuple, containing identifiers such as \texttt{tac\_page\_visible}, \texttt{fcsmc\_final\_go\_result\_visible}, and \texttt{ins\_ok\_text\_visible}.
Configuration is loaded from \texttt{vision\_facts.yaml} through a filesystem-stat-cached, LRU-cached loader (\texttt{load\_vision\_facts\_config}), which normalises fact specifications (sticky flag, TTL in milliseconds, intended regions, associated step IDs) and step bindings (\texttt{all\_of} and \texttt{any\_of} conditions).

The core merging logic in \texttt{merge\_vision\_fact\_observation} implements three key semantics.
First, \emph{sticky preservation}: a fact whose prior state is \texttt{seen}, whose \texttt{sticky} flag is \texttt{True}, and whose TTL has not expired will not be overwritten by a subsequent \texttt{not\_seen} or \texttt{uncertain} observation---only a later \texttt{seen} or expiry can replace it.
Second, \emph{TTL-based expiry}: \texttt{prune\_expired\_facts} discards any fact whose \texttt{expires\_at\_wall\_ms} precedes the current wall clock.
Third, \emph{step binding satisfaction}: \texttt{facts\_satisfy\_step\_binding} checks that all facts in the \texttt{all\_of} list are \texttt{seen} and that at least one fact in the \texttt{any\_of} list (if defined) is \texttt{seen}.
% Evidence: core/vision_facts.py lines 1-552

For the \texttt{fcsmc\_final\_go\_result\_visible} fact (step S18), an additional coercion layer checks the \texttt{result\_kind} field and the \texttt{evidence\_note} text against a set of regular expressions (e.g., \texttt{"MC1:\ GO"}, \texttt{"FCSA:\ GO"}).
A \texttt{seen} state is only retained if the classification yields \texttt{"final\_go"}; intermediate states such as \texttt{"intermediate\_go"}, \texttt{"in\_test"}, or \texttt{"not\_ready"} are coerced to \texttt{"not\_seen"}, and anything else is coerced to \texttt{"uncertain"}.
% Evidence: core/vision_facts.py lines 293-306 (_coerce_s18_result_fact_state, _normalize_result_kind)

\subsection{Dynamic HelpResponse Schema}

The module \texttt{core/llm\_schema.py} generates the JSON Schema for structured help responses at runtime, not from a static file.
The function \texttt{build\_help\_response\_schema} receives three lists of enum values---step identifiers from the step registry (or pack configuration), overlay target names from the UI map, and error category codes from the taxonomy---and constructs a Draft 2020-12 schema with four required top-level keys: \texttt{diagnosis}, \texttt{next}, \texttt{overlay}, and \texttt{explanations}.
A particularly detailed part of the schema is the \texttt{overlay.evidence} array: for each overlay target, a conditional sub-schema (\texttt{if}/\texttt{then}) requires that the evidence array contains at least one item referencing that target, thereby enforcing that the model cannot request an overlay without citing the evidence source from which it inferred the target.
The schema also requires each evidence item to carry a \texttt{type} field restricted to the set \texttt{\{"var", "gate", "rag", "delta", "visual"\}}, a non-empty \texttt{ref} and \texttt{quote}, and a \texttt{grounding\_confidence} between $0.0$ and $1.0$.
The computed schema is cached keyed on the filesystem modification times and sizes of its source files, so schema regeneration is avoided during long-running sessions.
% Evidence: core/llm_schema.py lines 132-325

\subsection{Data Contracts}

Two versions of data contracts coexist.
The v1 types in \texttt{core/types.py} define four core dataclasses used throughout the runtime: \texttt{Observation} (timestamped simulator state with optional procedure hint and tags), \texttt{TutorRequest} (learner-initiated help intent with an observation reference and context dictionary), \texttt{TutorResponse} (tutor output with status, message, overlay actions, and explanations), and \texttt{Event} (general-purpose log entry with session identifier, event kind, versioned payload, and extensible metadata).
All four carry UUID-based identifiers, ISO-8601 wall-clock timestamps, and a \texttt{to\_dict} serialisation method.
% Evidence: core/types.py lines 1-94

The v2 types in \texttt{core/types\_v2.py} extend the contract space with simulator-specific structures: \texttt{DcsObservation} (raw DCS-BIOS frame with sequence number and cockpit dictionary), \texttt{TelemetryFrame} (enriched state with normalised \texttt{vars}, BIOS snapshot, and cockpit arguments), \texttt{VisionObservation} (screenshot metadata with frame identifier, layout identifier, capture timestamp, and image URI), \texttt{VisionFact} (individual visual fact with identifier, three-valued state, source frame reference, TTL, and evidence note), and \texttt{VisionFactObservation} (collection of facts returned by the extractor, carrying a trigger timestamp and frame identifier list).
% Evidence: core/types_v2.py lines 1-118

\subsection{Additional Core Modules}

Several supporting core modules complete the domain layer.
\texttt{core/vars.py} implements \texttt{VarResolver}, a telemetry variable resolver that evaluates restricted Python expressions (numeric arithmetic, boolean logic, comparisons, and a \texttt{num()} coercion function) to project raw BIOS data onto normalised state variables, while tracking \texttt{vars\_source\_missing} for key-level observability.
% Evidence: core/vars.py lines 1-311
\texttt{core/knowledge.py} provides a \texttt{BM25Retriever} class implementing standard BM25 term weighting with Okapi-style IDF, used by the local knowledge adapter for document snippet retrieval.
% Evidence: core/knowledge.py
\texttt{core/overlay.py} defines the \texttt{OverlayPlanner} class, which maps abstract target names (e.g., \texttt{battery\_switch}) to DCS-internal point codes using the procedure pack's UI map, and produces \texttt{OverlayIntent} objects with one of three intents: \texttt{highlight}, \texttt{clear}, or \texttt{pulse}.
% Evidence: core/overlay.py lines 1-64
\texttt{core/step\_signal\_metadata.py} provides observability status normalisation and \texttt{compute\_requires\_visual\_confirmation}, which determines whether a step requires visual evidence based on its \texttt{observability} field and \texttt{evidence\_requirements} list.
% Evidence: core/step_signal_metadata.py
\texttt{core/help\_cycle\_audit.py} defines the canonical set of help-cycle audit fields (\texttt{generation\_mode}, \texttt{vision\_used}, \texttt{frame\_id}, \texttt{sync\_delta\_ms}, etc.) and a normalisation function used consistently by both the live runtime and the replay path.
% Evidence: core/help_cycle_audit.py

\section{Telemetry and DCS Integration}\label{sec:impl-telemetry}
% Evidence: adapters/telemetry_pipeline.py, adapters/delta_sanitizer.py,
%           adapters/delta_aggregator.py, adapters/dcs_bios/receiver.py,
%           adapters/dcs_bios/bios_ui_map.py, packs/fa18c_startup/telemetry_map.yaml,
%           packs/fa18c_startup/delta_policy.yaml
% Claims: C-TELEM-01

The telemetry integration pipeline operates in four stages, each implemented by a dedicated adapter module.

\textbf{Raw DCS-BIOS ingestion.}
The \texttt{DcsBiosRawReceiver} class opens a UDP socket and listens for DCS-BIOS binary export frames.
Raw frames are decoded as UTF-8 JSON and written directly to a JSONL file without processing, enabling offline replay of BIOS data independently of the live runtime.
The companion \texttt{DcsBiosReceiver} class provides a higher-level interface that parses BIOS payloads, enforces monotonic sequence numbers, merges full-state deltas into an accumulated state dictionary, and produces \texttt{Observation} objects for consumption by the tutoring runtime.
% Evidence: adapters/dcs_bios/receiver.py lines 1-60; live_dcs.py lines 24-25

\textbf{BIOS-to-UI mapping.}
The \texttt{BiosUiMapper} class loads \texttt{bios\_to\_ui.yaml} from the procedure pack, mapping DCS-BIOS key names to abstract UI target identifiers.
This mapping enables the delta aggregation pipeline and the deterministic step inference module to translate raw telemetry changes into semantically meaningful UI references.
% Evidence: adapters/dcs_bios/bios_ui_map.py

\textbf{Variable resolution and enrichment.}
\texttt{enrich\_bios\_observation} in \texttt{adapters/telemetry\_pipeline.py} applies the \texttt{VarResolver} to a \texttt{TelemetryFrame}, producing normalised key--value pairs in the \texttt{vars} dictionary.
The resolver projects from four reference roots (\texttt{bios}, \texttt{lo}, \texttt{cockpit\_args}, \texttt{vars}) via expressions defined in \texttt{telemetry\_map.yaml}.
Variables whose source references are absent or whose expression evaluates to \texttt{None} are tracked in \texttt{vars\_source\_missing}, providing downstream components with key-level observability.
% Evidence: adapters/telemetry_pipeline.py lines 1-80; core/vars.py lines 256-297

\textbf{Delta sanitisation and aggregation.}
The \texttt{DeltaSanitizer} class (in \texttt{adapters/delta\_sanitizer.py}) applies a configurable \texttt{DeltaPolicy} loaded from \texttt{delta\_policy.yaml} to suppress spurious state changes.
The policy specifies per-variable numeric-change thresholds, debounce windows, and filtering rules.
Validated changes are emitted as \texttt{SanitizedDelta} records carrying kept and dropped change counts with per-reason breakdowns.
The \texttt{DeltaAggregator} (in \texttt{adapters/delta\_aggregator.py}) accumulates sanitised deltas over a configurable time window and compresses them into a \texttt{DeltaSummary} containing recent UI targets (mapped through \texttt{BiosUiMapper}), top-$k$ key changes, and dropped-change statistics.
These summaries are included in the help-cycle prompt context and in the recent-actions ring buffer used by the live runtime.
% Evidence: adapters/delta_sanitizer.py lines 1-60; adapters/delta_aggregator.py lines 1-60

\textbf{Telemetry frame schema.}
The v2 telemetry frame schema (\texttt{simtutor/schemas/v2/telemetry\_frame.json}) defines the canonical structure of enriched telemetry records, including wall-clock timestamp, session identifier, BIOS snapshot, cockpit arguments, normalised variables, and optional low-level outputs.
All live and replay paths validate telemetry frames against this schema at the point of emission.
% Evidence: simtutor/schemas/v2/telemetry_frame.json

The entire telemetry pipeline runs as a continuous background thread in the live runtime, independent of any specific help cycle.

\section{Structured Help Generation}\label{sec:impl-help}
% Evidence: adapters/prompting.py, adapters/openai_compat_model.py,
%           adapters/ollama_model.py, adapters/model_stub.py,
%           adapters/json_extract.py, adapters/response_mapping.py,
%           adapters/action_executor.py, adapters/step_inference.py,
%           core/llm_schema.py
% Claims: C-ARCH-03

The help generation subsystem transforms a tutor request and its assembled context into a validated, executable tutor response.
It proceeds through six stages.

\subsection{Prompt Construction}

The function \texttt{build\_help\_prompt\_result} in \texttt{adapters/prompting.py} assembles the full prompt sent to the language model.
It includes: the current simulator state (\texttt{vars}), sanitised recent deltas, candidate procedure steps with their observability status and visual confirmation requirements, the deterministic step hint and its missing conditions list, the overlay target allowlist, BM25-retrieved knowledge snippets (up to five, each truncated to 220 characters), and, when available, the current vision fact summary.
The prompt is subject to a hard character cap (9000) with an estimated token limit of 2400.
Interaction policy rules for switch position, knob rotation, and button click conventions are included in either Chinese or English.
% Evidence: adapters/prompting.py lines 1-80

\subsection{Model Adapter}

The model adapter layer supports three backends through a common interface.
\texttt{OpenAICompatModel} (in \texttt{adapters/openai\_compat\_model.py}) posts chat-completion requests to an OpenAI-compatible endpoint, appending \texttt{/v1/chat/completions} to the configured base URL.
It requires an API key, supports configurable timeout and max-token limits, and can be toggled to multimodal mode.
\texttt{OllamaModel} (in \texttt{adapters/ollama\_model.py}) is a zero-dependency adapter for local Ollama servers.
\texttt{ModelStub} (in \texttt{adapters/model\_stub.py}) returns a fixed deterministic response for testing, enabling the full help-generation pipeline to be exercised without an external model service.
All adapters return a raw text response through a unified call interface.
% Evidence: adapters/openai_compat_model.py, adapters/ollama_model.py,
%           adapters/model_stub.py, model_access.md

\subsection{JSON Extraction with Minimal Repair}

Model responses are not guaranteed to contain only valid JSON.
The module \texttt{adapters/json\_extract.py} implements a \texttt{parse\_first\_json} function with a deliberately narrow repair set, limited to four transformations: (1) removal of balanced Markdown code fences (triple-backtick JSON blocks), (2) removal of leading \texttt{<think>...</think>} blocks, (3) dropping non-JSON prefix text before the first \texttt{\{} or \texttt{[}, and (4) dropping suffix text after the closing brace or bracket.
Any transformation outside this set is rejected.
The extraction uses a stack-based parser that tracks string quoting and escape sequences to correctly locate balanced JSON delimiters.
Each extraction returns a \texttt{JsonExtractionResult} recording whether repairs were applied and enumerating the specific repair reasons.
% Evidence: adapters/json_extract.py lines 1-160

\subsection{Schema Validation}

The extracted JSON object is validated against the runtime-generated HelpResponse schema (Section~\ref{sec:impl-core}) using \texttt{Draft202012Validator} from the \texttt{jsonschema} library.
Validation errors are reported with JSON Path locations derived from the validator's error path.
The schema enforces four categories of constraint: (1) required top-level keys, (2) enum membership for step identifiers and error category codes, (3) overlay target uniqueness and allowlist membership, and (4) evidence-item presence for every overlay target mentioned.
% Evidence: core/llm_schema.py lines 345-360

\subsection{Response Mapping and Evidence Grounding}

The function \texttt{map\_help\_response\_to\_tutor\_response} in \texttt{adapters/response\_mapping.py} translates the validated HelpResponse into a runtime \texttt{TutorResponse}.
It resolves overlay targets to DCS-internal element identifiers through the \texttt{OverlayPlanner}, which consults \texttt{ui\_map.yaml}.
The mapping function also validates that every overlay target cited in the response has at least one evidence reference whose prefix (\texttt{VARS.}, \texttt{GATES.}, \texttt{VISION\_FACTS.}, \texttt{RAG\_SNIPPETS.}, or \texttt{DELTA\_KEYS.}) matches a key actually present in the help-cycle context.
Targets without grounding evidence are rejected, and the rejection is recorded in the response metadata.
Explanations and diagnosis fields are passed through as-is.
The \texttt{TutorResponse} status is set to \texttt{"ok"} on full success and to \texttt{"partial"} or \texttt{"fallback"} when mapping failures occur.
% Evidence: adapters/response_mapping.py lines 1-60; adapters/evidence_refs.py lines 1-60

\subsection{Deterministic Fallback}

When no model is available, model output fails JSON extraction or schema validation, or response mapping produces an empty or invalid result, the system falls back to deterministic step inference.
The class \texttt{StepInferenceResult} (in \texttt{adapters/step\_inference.py}) examines the active step, evaluates unsatisfied gating rules, identifies missing conditions, maps condition references to likely UI targets via a hard-coded lookup table, and produces a text hint restricted to the currently active step.
By default, deterministic fallback does not trigger overlay highlights unless a local rule can prove a unique, valid target given the current telemetry state.
The fallback result is logged with the reason for fallback in the help-cycle audit metadata.
% Evidence: adapters/step_inference.py lines 1-60; core/step_hint.py

\subsection{Action Execution Safety}

The \texttt{OverlayActionExecutor} in \texttt{adapters/action\_executor.py} enforces three safety constraints on all actions before dispatching them to DCS via UDP.
First, only actions of type \texttt{"overlay"} are executable---no control injection, no key emulation, no click simulation.
Second, every overlay target is checked against the UI target allowlist derived from the pack's \texttt{ui\_targets} field; targets not in the allowlist are rejected and logged.
Third, at most one target may be highlighted at a time (\texttt{max\_targets=1}).
When a new highlight is requested, a prior active highlight is automatically cleared to prevent visual clutter.
The \texttt{pulse} intent uses a blocking sleep (\texttt{ttl\_s}) before dispatching a clear command, which blocks the calling thread but guarantees complete pulse delivery.
A configurable acknowledgement receiver (\texttt{DcsOverlayAckReceiver}) can optionally verify delivery by listening for UDP acknowledgement messages from the Lua-side overlay script.
% Evidence: adapters/action_executor.py lines 1-80; adapters/dcs/overlay/sender.py

\section{VLM Visual Fact Extraction}\label{sec:impl-vlm}
% Evidence: adapters/vision_fact_extractor.py, adapters/vision_fact_prompting.py,
%           adapters/openai_compat_multimodal.py, adapters/vision_sync.py,
%           adapters/vision_capture_trigger.py, core/vision_facts.py
% Claims: C-VLM-01, C-VLM-02

The VLM visual fact extraction runtime is implemented as a core, independently operable subsystem that communicates with the tutoring runtime through structured observations.

\subsection{Capture Trigger and Frame Selection}

When the active step is vision-priority (S08, S15, or S18) and a help request arrives, a capture request is dispatched to DCS via UDP using \texttt{build\_capture\_request\_payload} in \texttt{adapters/vision\_capture\_trigger.py}.
The Lua-side \texttt{SimTutor.lua} script renders the three primary cockpit displays (left DDI, AMPCD, right DDI) into a single composite PNG image.
The Python-side \texttt{BufferedVisionSession} (in \texttt{adapters/vision\_sync.py}) maintains a sliding buffer of recent vision observations and performs frame selection: by default, it retrieves both a pre-trigger frame (the most recent frame immediately before the trigger event within a configurable sync window of 250 ms) and the trigger frame itself.
If a pre-trigger frame is unavailable within the window, the session falls back to trigger-frame-only mode.
Frame staleness and sync miss reasons are recorded in the frame payload metadata.
% Evidence: adapters/vision_sync.py lines 1-60; adapters/vision_capture_trigger.py

\subsection{Multimodal Payload Construction}

The selected candidate frames are converted into a multimodal chat-completion payload by \texttt{build\_multimodal\_image\_contents} in \texttt{adapters/openai\_compat\_multimodal.py}.
Local frame files under a configurable root directory are read and base64-encoded as \texttt{data:} URLs with MIME type detection.
Remote URLs and inline data URLs are rejected.
A configurable maximum file size guards against accidentally large images.
The function produces a list of \texttt{image\_url} content blocks, each tagged with the frame's role (\texttt{"pre\_trigger"} or \texttt{"trigger"}), which are inserted alongside the text prompt into the messages array of the OpenAI-compatible request.
% Evidence: adapters/openai_compat_multimodal.py lines 1-80

\subsection{13-Fact Prompt}

The prompt for visual fact extraction is built by \texttt{build\_vision\_fact\_prompt} in \texttt{adapters/vision\_fact\_prompting.py}.
It enumerates all 13 configured facts, describes the three-region composite-panel layout (top: left DDI; middle: AMPCD; bottom: right DDI), and provides detailed decision-boundary instructions for each fact: for example, \texttt{tac\_page\_visible} requires the actual TAC page content, not merely a TAC menu label; \texttt{fcsmc\_final\_go\_result\_visible} requires final GO results for all four channels (MC1, MC2, FCSA, FCSB); \texttt{ins\_ok\_text\_visible} requires clearly readable \texttt{OK} text near the INS alignment block.
The prompt is available in both Chinese and English via a \texttt{lang} parameter.
% Evidence: adapters/vision_fact_prompting.py lines 1-80

\subsection{Model Response Sanitisation}

The raw model output is parsed as JSON and sanitised by \texttt{\_sanitize\_model\_response} in \texttt{adapters/vision\_fact\_extractor.py}.
The sanitisation function strips unknown top-level keys, rejects fact array entries that are not mappings, rejects entries with missing required fields (\texttt{fact\_id}, \texttt{state}, \texttt{evidence\_note}), and rejects fact entries whose \texttt{fact\_id} does not belong to the valid fact ID set defined in the configuration.
Only three fact states are accepted: \texttt{"seen"}, \texttt{"not\_seen"}, and \texttt{"uncertain"}.
A dynamic JSON Schema is generated on-the-fly from the allowed fact IDs using \texttt{\_vision\_fact\_response\_schema}, and the sanitised output is validated against it via \texttt{Draft202012Validator}.
% Evidence: adapters/vision_fact_extractor.py lines 1-80

\subsection{Fact Merging and Backend Compatibility}

The sanitised facts are merged into the runtime visual fact snapshot through \texttt{merge\_vision\_fact\_observation} (Section~\ref{sec:impl-core}), which applies sticky preservation and TTL-based expiry before updating the snapshot.
The VLM backend compatibility layer in \texttt{adapters/openai\_compat\_multimodal.py} handles provider-specific error conditions, including detection of \texttt{400} responses indicating multimodal or JSON-schema-unsupported backends, and distinguishes between genuine errors and the \texttt{null} payload sent by DashScope for multimodal responses.
When the VLM is unavailable or the multimodal request fails, the help cycle proceeds with telemetry and knowledge only, recording the reason in the vision fallback metadata.
% Evidence: adapters/openai_compat_multimodal.py lines 1-30

\subsection{VR Compatibility}

The current VLM runtime extracts facts from the composite-panel layout (left DDI, AMPCD, right DDI).
Composite-panel capture has been validated for compatibility in VR mode (Quest~3), using VR\_MIRROR and VR\_allow\_MFD\_out\_of\_HMD configurations.
The vision port abstraction supports alternative frame sources without changes to the extraction or merging logic.
% Evidence: ports/vision_port.py

\section{Replay and Logging Infrastructure}\label{sec:impl-replay}
% Evidence: core/event_store.py, simtutor/runner.py, simtutor/replay_eval.py,
%           core/scoring.py, core/interaction_metrics.py
% Claims: C-RUNTIME-01

\subsection{JSONL Event Store}

The \texttt{JsonlEventStore} class in \texttt{core/event\_store.py} is the sole persistence mechanism for runtime events.
It implements an append-only writer with immediate \texttt{flush} after each write, ensuring crash-safe logging.
The store supports context-manager usage (\texttt{\_\_enter\_\_} / \texttt{\_\_exit\_\_}) and provides a static \texttt{load} method that reads an entire JSONL file into memory as a list of dictionaries.
Event serialisation accepts both \texttt{Event} dataclass instances and plain dictionaries, delegating to \texttt{Event.to\_dict()} when the former is supplied.
% Evidence: core/event_store.py lines 1-43

\subsection{Replay and Validation}

The replay module in \texttt{simtutor/runner.py} provides two entry points.
\texttt{run\_simulation} drives a full simulation using a \texttt{MockEnvAdapter} that replays pre-recorded observation sequences, coordinated with a \texttt{ProcedureEngine} instance, and writes the resulting event log to a timestamped JSONL file.
\texttt{replay\_log} validates an existing event log by replaying it against a procedure pack: it reconstructs the step state machine, verifies that each event's step status transitions are legal (e.g., a step cannot be completed before it is activated), and returns a boolean success flag together with a diagnostic message.
Replay validation includes checks for monotonic sequence numbers and wall-clock timestamps in telemetry traces.
% Evidence: simtutor/runner.py lines 1-80

The replay evaluation infrastructure in \texttt{simtutor/replay\_eval.py} extends replay to support suite-driven evaluation: a YAML suite file specifies a pack path, a set of test cases, model configuration, and optional vision frame directories, enabling systematic regression replay at the telemetry level and for vision sidecar scenarios.
% Evidence: simtutor/replay_eval.py lines 1-60

\subsection{Interaction Metrics}

The \texttt{compute\_interaction\_metrics} function in \texttt{core/interaction\_metrics.py} derives behavioural metrics from event logs.
It computes: stall time per step (total and maximum, derived from \texttt{step\_activated} to \texttt{step\_completed} intervals), help request count, LLM trigger count (tutor responses with model metadata), UI click count and failure count, and highlight/clear request and acknowledgement counts.
The output is an \texttt{InteractionMetrics} dataclass with a \texttt{to\_dict} serialisation method.
% Evidence: core/interaction_metrics.py lines 1-103

\subsection{Current Limitations}

The logging and replay infrastructure has been exercised with synthetic regression scenarios (mock environments, pre-recorded observation sequences, and offline BIOS captures).
End-to-end replay of full multimodal sessions with synchronised vision frames from live human-in-the-loop runs has not yet been validated.

\subsection{CLI Commands}

The \texttt{simtutor} package provides a command-line interface through \texttt{simtutor/\_\_main\_\_.py}.
The following commands are implemented:

\begin{description}
\item[\texttt{run}.] Executes a simulation using a \texttt{MockEnvAdapter} with a pre-recorded scenario file and writes the event log to a timestamped JSONL file.
\item[\texttt{replay}.] Validates an existing event log against a procedure pack, checking step ordering and state-machine consistency.
\item[\texttt{score}.] Scores an event log using the scoring engine, producing omission counts, state-violation counts, and a total error score.
\item[\texttt{record-vlm}.] Runs VLM fact extraction on a set of vision observations and records the predictions for benchmarking.
\item[\texttt{replay-bios}.] Replays a raw DCS-BIOS capture (\texttt{dcs\_bios\_raw.jsonl}) through the telemetry pipeline and optionally invokes the help generation loop, producing a new timestamped event log.
\item[\texttt{validate}.] Validates JSONL files against a named schema from the schema registry (e.g., \texttt{dcs\_bios\_frame}, \texttt{telemetry\_frame}, \texttt{vision\_fact\_observation}).
\end{description}
% Evidence: simtutor/__main__.py lines 1-80

All commands accept a \texttt{--model-provider}, \texttt{--model-name}, \texttt{--model-base-url}, and \texttt{--model-timeout-s} argument, allowing model configuration to be overridden at the command line.
The \texttt{--lang} flag switches between Chinese (\texttt{zh}) and English (\texttt{en}) prompt and output languages.
% Evidence: simtutor/__main__.py lines 69-80

\subsection{Live Runtime Orchestration}

The module \texttt{live\_dcs.py} is the primary live runtime entrypoint.
It orchestrates the following continuous loop:

\begin{enumerate}
\item A \texttt{DcsBiosRawReceiver} or \texttt{DcsBiosReceiver} ingests UDP frames from DCS.
\item Each raw frame is enriched through \texttt{enrich\_bios\_observation} to produce normalised state variables.
\item When a help trigger is received (hotkey via \texttt{WindowsGlobalHelpTrigger} or UDP message), a help cycle begins:
  \begin{itemize}
  \item The deterministic step hint is computed via \texttt{infer\_step\_id}, evaluating pack gates against current telemetry.
  \item If the active step requires visual confirmation, a vision capture trigger is sent and the VLM fact extractor is invoked.
  \item A BM25 grounding query is built and knowledge snippets are retrieved.
  \item The full prompt is assembled and sent to the model adapter.
  \item The model response is parsed, validated, and mapped to a \texttt{TutorResponse}.
  \item Overlay actions are executed via \texttt{OverlayActionExecutor}, with allowlist and cardinality enforcement.
  \item The complete help cycle (request, response, actions, vision facts, fallback reason if any) is logged as \texttt{Event} records.
  \end{itemize}
\item The loop continues until terminated.
\end{enumerate}

The live runtime supports both real-time DCS operation and replay of pre-recorded BIOS captures through a shared code path, controlled by the \texttt{--replay-bios} flag.
All threading (BIOS receiver, overlay acknowledgement receiver, help cycle processing) is managed via Python standard-library threading primitives with queue-based inter-thread communication.
% Evidence: live_dcs.py lines 1-100

\subsection{DCS Lua Scripts}

Three categories of Lua scripts execute inside the DCS process:

\begin{description}
\item[State export.] \texttt{Export.lua} loads DCS-BIOS and the SimTutor integration module, establishing the state-export chain.
\item[Overlay rendering.] \texttt{VRHilite.lua} binds a UDP socket on port 7778 and listens for plain-text overlay commands (\texttt{HIGHLIGHT <pnt>}, \texttt{CLEAR}, \texttt{PULSE <pnt> <ttl\_s>}). Highlights are rendered via DCS's \texttt{a\_cockpit\_highlight} / \texttt{a\_cockpit\_remove\_highlight} API accessed through \texttt{net.dostring\_in}.
\texttt{SimTutorHighlight.lua} provides an alternative rendering path for SimTutor-specific highlight contexts.
\item[SimTutor integration.] \texttt{SimTutor.lua} loads \texttt{SimTutor Function.lua} (which contains the capture and export logic) and installs the export chain. \texttt{SimTutorDcsBiosHub.lua} bridges SimTutor-specific state queries to the DCS-BIOS data model.
\end{description}
% Evidence: DCS/Scripts/Export.lua, DCS/Scripts/Hooks/VRHilite.lua,
%           DCS/Scripts/SimTutor/SimTutor.lua

\subsection{Model Provider Configuration}

Model access is configured through environment variables with a unified naming convention (Section~\ref{sec:design-arch}).
The live runtime validates all required configuration at startup, emitting a non-sensitive summary (provider, model name, timeout, language, base URL) and rejecting the session with a clear error message if any required variable is missing.
API keys are never included in log output or exception messages, enforced by the \texttt{redact\_sensitive\_text} function in \texttt{core/security.py}.
