\chapter{Methods: Visual Fact Adaptation and Pilot Protocol}\label{ch:methodology}

Chapter~\ref{ch:system-design} presented the runtime architecture that keeps
tutor output downstream of evidence and upstream of validation. This chapter
describes how the remaining empirical evidence is produced, curated, and
evaluated. The method is organised around a practical question: how can a small
set of reviewed cockpit images, structured labels, and formative VR sessions
become auditable evidence for a machine-learning tutoring system?

The chapter therefore treats the runtime, the VLM data pipeline, and the pilot
as linked evidence protocols rather than as implementation inventories. For
RQ1, it records which runtime signals are allowed to support replay and pilot
analysis. For RQ2, it defines how screenshots become reviewed visual-fact
labels, training rows, LoRA adapters, and independent holdout benchmarks. For
RQ3, it documents the formative VR pilot protocol and keeps its claims
descriptive: the pilot can inform feasibility and interaction patterns, but not
infer learning gains.

% ===========================================================================
\section{Procedure Runtime and Telemetry Grounding}\label{sec:method-telemetry}

Telemetry and procedure gates provide the state evidence on which the help
cycle depends. Raw simulator telemetry fields are projected onto normalised runtime
variables, while unavailable sources are tracked separately in
\texttt{vars\_source\_missing}. This distinction matters methodologically: a
known false value can support corrective guidance, but an unobserved value can
only support uncertainty-aware guidance or fallback.

Each procedure step then evaluates precondition and completion gates over these
variables. The gate DSL covers threshold checks, ranges, boolean flags, and
elapsed-time conditions. Missing, source-missing, or sentinel values fail with
diagnostic reasons rather than being silently coerced, and those reasons are
logged with the help-cycle context. Recent learner action is represented through
sanitised telemetry deltas, using per-variable thresholds, debounce windows, and
filtering before a compact prompt-safe summary is produced. If model output is
unavailable or invalid, the deterministic fallback computes a conservative hint
from the active step, unsatisfied gates, recent actions, and evidence
availability; overlay guidance remains suppressed unless a local rule identifies
a unique valid target.

\section{Knowledge Grounding and Source Policy}\label{sec:method-knowledge}

Retrieved procedural knowledge supplies textual context for generated help, but
it is deliberately source-controlled. The local retrieval adapter indexes
curated procedure and aircraft documentation at sentence level and ranks
snippets with BM25~\citep{robertson2009bm25}. A grounding query is constructed
from the active step, its description, and the current observation; the top
snippets are included in the help-cycle context.

A declarative source policy restricts retrieval to allowed document sources.
This prevents the model from receiving procedure variants outside the active
procedure pack, such as carrier-specific instructions when the current profile
is an airfield cold start. Retrieval is therefore not a general document search
facility. It is a controlled evidence channel whose scope is part of the
procedure configuration.

\section{Visual Fact Data Pipeline}\label{sec:method-vlm-pipeline}

The visual fact pipeline is the main methodology for RQ2. It turns DCS World cockpit
screenshots into supervised examples and then into a benchmarked visual fact
extractor. The pipeline is designed for traceability: a benchmark error should
be traceable back to the model prediction, the human-reviewed label, the
pre-label, and the original image. This reflects dataset-documentation practice
that treats motivation, composition, collection, recommended use, and provenance
as part of the dataset artifact rather than as external notes
\citep{gebru2021datasheets}.

Figure~\ref{fig:vlm-pipeline} shows the pipeline as a loop. Holdout failures
are not only final results; they can reveal weaknesses in the ontology and
guide later data collection.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{figures/fig_vlm_pipeline.png}
  \caption{VLM adaptation pipeline. DCS World composite screenshots are pre-labelled,
  human-reviewed, converted into bilingual supervised fine-tuning rows, adapted
  with LoRA, evaluated on independent holdout sets, and used to drive ontology
  revision.}
  \label{fig:vlm-pipeline}
  \Description[VLM adaptation pipeline]{A two-row pipeline shows cockpit
  screenshots moving through AI pre-labels, human review, reviewed labels,
  bilingual supervised fine-tuning rows, LoRA adapters, independent holdout
  benchmarks, error review, ontology revision, and runtime visual-fact
  extraction.}
\end{figure}

\begin{enumerate}
\item \textbf{Screenshot capture.} DCS World renders the left DDI, AMPCD, and right
DDI into one composite-panel image. The same composite layout is used for data
collection, pre-labelling, training, benchmarking, and runtime inference. This
keeps the input distribution stable across the method.

\item \textbf{VLM pre-labelling.} An external VLM produces initial labels and
evidence notes for each image. Pre-labelling is used as an annotation aid and
workflow provenance, not as ground truth or as a benchmark baseline.

\item \textbf{Human review.} Pre-labelled samples are reviewed in Label
Studio~\citep{tkachenko2020labelstudio}. The reviewer corrects fact states and
evidence notes while preserving a link to the raw image and pre-label.

\item \textbf{Reviewed JSONL export.} The reviewed export is the authoritative
ground-truth artifact for downstream training and evaluation.

\item \textbf{Bilingual SFT generation.} Each reviewed image yields an English
and a Chinese training row with the same image and fact labels. The assistant
target is structured JSON containing visual facts and a short summary; external
management fields such as frame identifiers, file paths, and confidence fields
are excluded from the target.

\item \textbf{LoRA adaptation.} The SFT rows are used to train LoRA adapters
for VLM backbones~\citep{hu2021lora}. The implementation uses PEFT adapter
definitions~\citep{mangrulkar2022peft}, TRL supervised fine-tuning
infrastructure~\citep{vonwerra2020trl}, and Unsloth acceleration for 4-bit VLM
training~\citep{unsloth2024}.

\item \textbf{Holdout benchmark and revision.} Base and LoRA configurations are
evaluated on independent holdout sets. Errors are inspected at fact level,
especially for completion-critical facts, and the resulting failure modes feed
back into ontology and dataset revisions.
\end{enumerate}

The method intentionally keeps the VLM's task narrow. The model is trained to
report visual facts with states \texttt{seen}, \texttt{not\_seen}, or
\texttt{uncertain}. It is not trained to decide procedure completion or produce
tutor actions. Those decisions remain in the procedure engine and harness.

\subsection{Annotation Unit and Decision Boundaries}

The annotation unit is one composite-panel screenshot paired with the complete
13-fact label vector. A sample is not labelled only for the fact that triggered
collection; every fact in the ontology is reviewed. This full-vector labelling
is important because the benchmark later evaluates complete visual snapshots.
It also prevents the training data from becoming a set of isolated positive
examples with poorly defined negatives.

Reviewers apply fact-specific decision boundaries. A page option label is not
the same thing as the page itself. A visible FCS-MC entry on a BIT root page is
not the FCS-MC subpage. A PBIT GO status is not the same as the final FCS-MC GO
result. HSI symbology without a coloured map layer is not sufficient for the
map-layer fact. INS OK must be readable near the alignment block rather
than inferred from the elapsed procedure phase. These rules are written into
the benchmark prompt and reflected in the ontology, so the model is trained and
evaluated against the same conceptual contract.

The \texttt{uncertain} label is used when the screenshot does not support a
clean decision. This includes blurred frames, partially obstructed display
regions, ambiguous text, or states that require temporal history rather than a
single image. The reviewer is not asked to guess what the simulator probably
did before or after the screenshot. That discipline keeps the VLM task aligned
with the runtime boundary: single-frame perception reports visible facts, while
procedure reasoning happens downstream.

Pre-labelling accelerates the process but does not define ground truth. The
external VLM's output is treated as an annotation proposal. Human review can
change the state, revise the evidence note, or preserve uncertainty. The final
reviewed JSONL, not the pre-label, is the source used for SFT and benchmark
scoring. This distinction is essential because otherwise the benchmark would
measure agreement with another model rather than agreement with reviewed visual
facts. The pre-label source is therefore part of the annotation trail, not part
of the evidence used to claim model accuracy.

The reviewed labels were not independently double-coded. They should therefore
be interpreted as single-reviewer, human-reviewed labels rather than as an
inter-rater-reliability study. The thesis claim is within-domain adapter
reliability on the reviewed artifact set; for later reliability studies,
especially for rare completion-critical facts, this remains a limitation.

Run-003 and Run-005 contain samples whose free-text summary field is blank
(82 and 25 samples respectively). These samples remain valid for the visual
fact task because every sample still contains a complete fact array. The
supervised target used by the runtime and benchmark is the structured fact
state, not the optional summary.

\subsection{Dataset Quality Checks}

The dataset pipeline applies several checks before a reviewed export is used for
training or benchmarking. First, every sample must include the expected fact
identifiers exactly once. Missing or duplicated fact IDs would make it unclear
whether a model error is visual or structural. Second, every fact state must be
one of the allowed states. Third, the image path must resolve to the composite
panel image used during review. Fourth, training and holdout sets are checked
for exact image overlap before the holdout metrics are interpreted as
independent evidence.

The quality checks do not guarantee that every label is perfect. They guarantee
that the data artifacts have the structure needed for a meaningful benchmark.
This is a different but important claim. In small-data adaptation, a few
ambiguous labels can have a visible effect, especially for rare positive facts.
The thesis therefore treats error analysis as part of the data workflow. If a
holdout error reveals that a fact definition is too close to a procedural
conclusion, the correct response is not simply to collect more data; it may be
to revise the ontology.

Run-005 is an example of data-centric correction. The original Run-003 training
source contained useful coverage but under-represented several rare states. The
composition-rebalance supplement intentionally increases exposure to those
states. This does not make the training set statistically representative of all
possible cockpit states, and it is not presented that way. Its role is
practical: expose the adapter to positive examples that matter for downstream
procedure evidence and then test behaviour on independent holdouts.

\subsection{Ontology Evolution: 8-Fact v1 to 13-Fact v2}

The first ontology contained eight facts over the composite cockpit panel. It
established that a small reviewed dataset could improve structured cockpit
fact extraction, but it also exposed a representation problem: some targets
mixed visual observation with procedural interpretation. The clearest case was
\texttt{ins\_go}, which asked a single-frame VLM to infer an INS completion
state rather than report directly visible evidence.

Figure~\ref{fig:ontology-evolution} illustrates the methodological correction.
Compound procedural targets were decomposed into locally observable visual
atoms, leaving temporal and procedural interpretation to the tutor runtime.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{figures/fig_ontology_evolution.png}
  \caption{Ontology evolution from 8-fact v1 to 13-fact v2. Compound targets
  such as \texttt{ins\_go} and broad FCS-MC completion facts were decomposed
  into locally verifiable visual atoms; the procedure engine then combines
  those observations with telemetry, phase, and timing evidence.}
  \label{fig:ontology-evolution}
  \Description[Visual-fact ontology evolution]{A before-and-after diagram shows
  the 8-fact ontology using compound labels such as ins go and FCS bit result,
  a central design rule that the VLM should report visible evidence only, and
  the 13-fact ontology with separate observable atoms such as INS text and FCS
  page or final GO visibility.}
\end{figure}

The current 13-fact ontology follows three design rules:

\begin{enumerate}
\item \textbf{Decompose compound targets.} The \texttt{ins\_go} target is
replaced by separate visual atoms for GRND alignment text and INS OK text. The
FCS-MC sequence is represented by page, intermediate-result, in-test, and
final-GO facts.

\item \textbf{Separate region from semantics.} Fact names describe the visible
state rather than encoding the display region in the identifier. Region
constraints are part of the ontology metadata.

\item \textbf{Keep facts locally observable.} Each fact should be decidable from
the composite image without requiring procedure history. The procedure engine
combines facts with telemetry, step bindings, and timing information later.
\end{enumerate}

This ontology discipline is central to the thesis. It defines the boundary
between perception and procedural reasoning: the VLM reports visual evidence,
while the runtime decides whether that evidence satisfies a procedural step.

\subsection{Training Recipe: Run-003 + Run-005x2}

The primary v2 training recipe combines Run-003 with a repeated Run-005
composition-rebalance supplement. Run-003 contributes 220 reviewed images,
exported bilingually as 440 SFT rows. Run-005 contributes 122 reviewed images,
exported bilingually as 244 rows; this supplement is included twice, yielding
488 rows. The final recipe therefore contains \textbf{928 SFT rows}.

Run-005 targets under-represented positive states from Run-003, including INS
OK text, FCS page X marks, and FCS-MC sub-state facts. The repeated supplement
is a deliberate composition rebalance strategy, not an independent validation
set. For that reason, generalisation claims are based on external holdouts
rather than on an internal same-pool evaluation split.

\subsection{Holdout Independence}

Two 13-fact v2 holdouts are used for the main evaluation. Run-002 newfacts
contains 50 images from an earlier capture session re-labelled under the
13-fact ontology. Run-004 random contains 100 randomly sampled cockpit-state
captures. Local overlap checks report zero exact image overlap between either
holdout and the Run-003 + Run-005 training union.

This is an exact-overlap claim, not a broader leakage audit. The thesis does
not claim perceptual-nearest-neighbour separation, scene-level independence, or
absence of visually similar cockpit states across training and holdout
captures. Those stronger split audits are appropriate future artifact work,
especially because cockpit displays can contain near-duplicate states even when
image identities differ.

The earlier Run-001 evaluation line is treated differently. Because it overlaps
with the training data pool, it is useful as a contaminated development
benchmark for checking schema learning and historical ontology behaviour, but
it is not used as independent evidence for v2 generalisation.

\section{LoRA Fine-Tuning Configuration}\label{sec:method-lora-config}

\subsection{Backbone Models and Comparison Strategy}

The primary adaptation line uses \texttt{Qwen/Qwen3.5-9B-Base} with the
Run-003 + Run-005$\times$2 recipe. Two supplementary backbones are included to
test whether the same data recipe remains meaningful under scale, version, and
family changes: \texttt{Qwen/Qwen3.6-27B} and \texttt{google/gemma-4-31B}
\citep{gemma2024,gemma32025}. These strings are the model identifiers used in
the local benchmark artifacts and serving setup; the citations provide
model-family context, not a claim that every local endpoint detail is described
by the public reports. In this thesis, "local deployment candidate" means a
candidate for the project's local serving path after successful base-model
serving, LoRA loading, and benchmark execution. It does not mean a generally
validated product model. Chapter~\ref{ch:evaluation} reports the numerical
results.

The comparison holds the main factors constant wherever possible: ontology,
training recipe, benchmark prompt, holdout sets, generation temperature, output
schema, and metric computation. Backbone-specific differences remain and are
therefore reported explicitly. Qwen-family runs apply LoRA to vision and
language modules; the Gemma run uses an all-linear LoRA configuration with
vision layers not separately fine-tuned. Full settings appear in
Appendix~\ref{ch:appendix}, Table~\ref{tab:lora-hyperparams-full}.

\subsection{Training Stack and Hyperparameters}

All backbone runs use 4-bit loading, LoRA rank $r=16$, $\alpha=16$, dropout
$0.0$, four epochs, learning rate $2 \times 10^{-4}$, effective batch size 4,
maximum sequence length 4096, seed 3407, warmup ratio 0.1, and weight decay
0.01. Adapter weights are saved separately from the base model.

The epoch count and LoRA rank are chosen for small-data domain adaptation.
With 928 SFT rows, the adapter must learn both the fixed JSON schema and the
visual boundaries of cockpit facts. A very small number of epochs may not teach
those boundaries reliably, while excessive training would risk memorising the
capture sessions. Rank 16 provides moderate adaptation capacity without turning
the adapter into a high-capacity task-specific model.

\subsection{Bilingual SFT and Composition Rebalance}

The bilingual SFT strategy creates two instruction variants per reviewed image:
one English and one Chinese. The image and fact labels remain identical. This
increases instruction-format coverage without requiring additional image
annotation. It does not replace the need for new cockpit states or hard
negative examples.

Composition rebalance is handled through Run-005. Because rare positive facts
are especially important for downstream procedure reasoning, the training
recipe increases their exposure by adding targeted captures and repeating the
Run-005 bilingual rows. The method therefore separates two questions: whether
the adapter can learn the ontology from the rebalanced training recipe, and
whether the learned extractor generalises to independent holdouts.

\subsection{Training Target Construction}

The SFT target is intentionally smaller than the runtime observation object.
It contains the short summary field and the array of fact objects with
\texttt{fact\_id}, \texttt{state}, and \texttt{evidence\_note}. It excludes
frame identifiers, file paths, confidence values, sticky/expiry metadata, and
procedure suggestions. Those excluded fields are runtime management metadata,
not visual labels. Including them would teach the model to emit data it cannot
observe from the image and would make the output harder to validate.

The target also avoids asking for explanatory prose beyond short evidence
notes. Long free-form explanations would make the SFT objective less focused
and introduce additional evaluation ambiguity. The downstream language model
can later turn facts into user-facing tutoring language. The VLM adapter is
trained to supply the visual facts that such language may reference.

This separation keeps the training recipe aligned with the system architecture.
The VLM is not rewarded for sounding helpful, predicting the next step, or
explaining the procedure. It is rewarded for returning a complete, parseable,
ontology-aligned fact vector. That is why benchmark gains in this thesis are
interpreted as perception-layer gains, not as evidence that the full tutor is
pedagogically better.

\section{Benchmark Protocol}\label{sec:method-benchmark}

\subsection{Metrics}

The benchmark compares model predictions against human-reviewed ground truth at
both sample and fact level. The metrics are selected to reflect downstream
runtime risk, following the general caution that metric choice shapes
classification interpretation and should be justified for the task
\citep{powers2011evaluation,opitz2024metrics}:

\begin{itemize}
\item \texttt{json\_valid\_rate}: proportion of samples with parseable JSON
output.
\item \texttt{schema\_valid\_rate}: proportion of samples whose JSON contains
the required fact identifiers exactly once and uses only valid states.
\item \texttt{fact\_accuracy}: three-class accuracy over all facts and samples.
\item \texttt{macro\_f1}: macro-averaged F1 over the three states, averaged
over facts.
\item \texttt{seen\_f1}: F1 for the positive \texttt{seen} class, averaged over
facts. This matters because missed or hallucinated visible states change
procedure evidence.
\item \texttt{sample\_exact\_match}: proportion of samples where all 13 facts
match the reviewed labels.
\item \texttt{critical\_false\_positive\_count}: count of completion-critical
facts predicted \texttt{seen} when the reviewed label is \texttt{not\_seen} or
\texttt{uncertain}.
\end{itemize}

Critical false positives are tracked separately because they are the most
dangerous visual error for the tutor. A false positive on a completion-critical
fact could make the procedure engine believe that a display state has been
observed when it has not.

\subsection{Base vs.\ LoRA Comparison}

Base and LoRA configurations receive the same prompt, images, generation
parameters, and output schema. Decoding uses temperature 0.0, maximum new tokens
1024, and seed 3407. Predictions are written to JSONL, parsed, normalised, and
scored without post-hoc filtering. The comparison artifact reports LoRA-minus-
base deltas, while Chapter~\ref{ch:evaluation} interprets those deltas.

\subsection{Benchmark Categories}

Benchmark runs are classified by evidence status. Contaminated development sets
come from the same data pool as training and are used only for regression and
historical interpretation. Held-out new-session benchmarks use independent
captures with zero exact training overlap. This distinction determines the
strength of the claim that can be made from a metric.

\subsection{Benchmark Artifacts}

Each benchmark run produces a standard directory with metrics for each model,
per-sample predictions, error JSONL files, per-fact score CSVs, comparison
summaries, human-readable reports, and charts. These artifacts form the
evidence chain for the technical results reported in Chapter~\ref{ch:evaluation}.

\subsection{Error Review Protocol}

The benchmark is followed by qualitative error review. The review focuses first
on critical false positives, because those are the errors most likely to create
unsafe evidence for a procedure gate. It then inspects false negatives for
vision-priority facts, because repeated false negatives can make the tutor ask
for unnecessary checks or fail to recognise progress. Finally, it inspects
schema and exact-match failures to identify whether the remaining problem is
formatting, visual ambiguity, or fact-definition mismatch.

This review is deliberately tied to the runtime use case. Aggregate accuracy
and \(F_1\) are insufficient because a tutor consumes errors asymmetrically. A
hallucinated FCS-MC final GO result is more serious than a conservative
\texttt{not\_seen} prediction for a page that can be rechecked. A
schema-invalid output is less visually interesting but more important
operationally because it triggers fallback. The benchmark protocol therefore
connects numerical metrics to the validation and degradation paths described
in Chapter~\ref{ch:system-design}.

\section{Human-Subject Pilot Methodology}\label{sec:method-pilot}

A small formative VR pilot study was conducted to gather descriptive evidence
about the tutor in use during the F/A-18C cold-start task. The pilot was not a
powered controlled experiment. Its purpose was to exercise the runtime in a
realistic VR setting, inspect interaction logs, and identify procedural error
patterns for later study design.

\subsection{Ethics, Consent, and Data Protection}

The pilot was conducted as a formative, non-clinical procedural training study.
The study operation protocol required a welcome and consent step before the VR
session. Participants were told that the study evaluated the training system
rather than personal ability, that they could stop at any time, and that they
could pause or terminate the session if VR discomfort occurred. The same
protocol instructed the experimenter not to provide procedural step hints
except for technical issues.

The thesis reports participants only with pseudonymous identifiers
P01--P09. Exported artifacts used for analysis contain simulator telemetry,
runtime events, tutor interactions, step coding, questionnaire fields, and
short comments; names, email addresses, and student identifiers are not reported
in the thesis. Questionnaire and comment evidence is reported descriptively,
aggregated where appropriate, and anonymised or paraphrased in the main text.
No formal external ethics-approval identifier is claimed in this thesis; the
study is therefore reported conservatively as a local master's-thesis
formative pilot with informed consent and no inferential human-subject
effectiveness claims.

Recruitment and assignment were handled as local convenience scheduling for a
master's-thesis pilot, not as random sampling. The retained analysis package is
organised by pseudonymous participant directories; raw participant artifacts
are not released as a public dataset. Some session metadata contain recording
references, but external video is not used as analysis evidence in this thesis
and no identifiable video, audio, names, email addresses, student identifiers,
or recruitment records are published. Access to non-public raw materials is
treated as project-internal for thesis preparation and supervisory review.
Participants could stop during the VR session, and withdrawal or deletion
requests would be handled while data remained identifiable to the author. The
thesis does not report monetary compensation and does not use any
compensation-dependent analysis.

\subsection{Participants and Conditions}

Nine participants (P01--P09) completed one trial each. The study used a
between-subjects design with non-random assignment based on scheduling
availability:

\begin{description}
\item[With tutor (n=4).] P04, P05, P08, and P09 received overlay highlights,
structured help text, telemetry-grounded step inference, and VLM visual fact
support where applicable.
\item[Without tutor (n=5).] P01, P02, P03, P06, and P07 received no tutor
assistance. Telemetry was still recorded for offline step inference and error
coding.
\end{description}

Participant experience profiles are reported in Appendix~\ref{ch:appendix},
Table~\ref{tab:pilot-participants}. Because assignment was not randomised and
the sample is small, condition comparisons are descriptive only.

\subsection{Task and Apparatus}

All trials used the 33-step F/A-18C cold-start procedure in DCS World on a Meta
Quest~3 via Quest Link. The composite cockpit panel was mirrored for
experimenter observation. Tutor-condition trials used the live runtime with
remote model inference through an OpenAI-compatible endpoint. A trial ended
when the participant completed the procedure or voluntarily stopped after being
unable to progress.

\subsection{Data Sources and Coding}

The export pipeline produced per-trial summaries, per-step coding files,
help-cycle logs for tutor trials, action timelines, quality-gate metadata, and
session summaries. Post-trial forms recorded participant experience, confidence
before the trial, raw NASA-TLX workload dimensions~\citep{hart1988nasa},
condition-specific tutor ratings where applicable, general custom user
ratings, and free-text comments.

Step errors were coded with five categories: omission (OM, a required action
was not completed), commission (CO, an unnecessary or wrong action was
performed), order error (OR, an action was performed in the wrong sequence),
prompting/assistance error (PA, interaction with the tutor or experiment setup
affected the step), and state violation (SV, the aircraft state contradicted
the expected condition). The automated coding output was reviewed manually
using telemetry, help-cycle logs, and action timelines; the human-coded columns
are the authoritative source for reported pilot results.

The manual review was a project-side reconstruction pass, not a blinded
multi-coder reliability study. It used the recorded telemetry, action
timeline, help-cycle evidence where available, and observation notes to decide
whether each step was confirmed and whether a manual error category applied.
Where automatic reconstruction disagreed with reviewed evidence, the review
rule is declared before the results rather than hidden inside the outcome
table.

The coding distinguishes \emph{not confirmed as completed} from \emph{coded
omission}. This distinction matters for without-tutor trials, where passive
logging did not run the VLM page checks used by the tutor condition. A
visual-only step may therefore remain unconfirmed in the \texttt{Completed}
column even when telemetry or action-timeline evidence prevents scoring it as
a participant omission. The results chapter reports confirmed-step counts and
manual error counts as separate descriptive measures.

\subsection{Questionnaire and Comment Instruments}

The post-trial form records raw NASA-TLX workload dimensions, not weighted
NASA-TLX. The thesis reports the raw average because the formative pilot was
not designed to estimate a psychometric workload effect. The form also records
pre-trial confidence, condition-specific tutor ratings where the tutor was
available, general user ratings, and short open comments. These tutor/user
ratings are custom post-trial items, not validated SUS, trust, or usability
instruments \citep{lee2004trust,visser2023trust}. The rating values are kept on
their recorded scale and are not normalised into a single composite
effectiveness score.

The comments are used cautiously. They are not treated as coded qualitative
themes with inter-rater reliability. Instead, they provide context for
observed log and questionnaire patterns. For example, comments about small
fixed checklist text help explain why a no-tutor participant could struggle in
VR even when a procedure list was technically available. Comments about the AI
identifying where the learner was stuck help explain why tutor-condition
participants may have perceived the system as useful even when assistance-
coupled errors remained.

This instrument design matches the pilot's formative status. The questionnaire
and comments can reveal perceived usefulness, interaction friction, and
trust-related signals that should shape the next study. They cannot establish
causal changes in workload, trust, usability, or learning. That boundary is
maintained in the results chapter by reporting questionnaire values only as
descriptive summaries and keeping task coding separate from questionnaire-
derived evidence.

\subsection{Analysis Approach}

The pilot analysis reports per-participant outcomes and condition-level
descriptive summaries. No null-hypothesis significance tests are performed.
Observed durations are documented but not interpreted as completion-time
comparisons because incomplete without-tutor trials ended at different stopping
points. Questionnaire values are reported as raw descriptive scores only. The
analysis focuses on completion status, manual error categories, tutor
interaction patterns such as help requests, VLM calls, overlay actions, and
fallback events, and short anonymised comments that clarify interaction
frictions.

\section{Summary}\label{sec:method-summary}

The methodology establishes the evidence chain used by the rest of the thesis.
Telemetry and retrieval provide controlled runtime context. The visual fact
pipeline produces a reviewed and benchmarked perception layer for RQ2. The
13-fact ontology separates perception from procedural reasoning. The LoRA
protocol uses matched data and holdouts to evaluate small-data adaptation
without relying on contaminated development sets. The pilot protocol provides
formative VR evidence for RQ3 while keeping its claims descriptive. Together,
these methods make the later results auditable without overstating what the
available evidence can prove.
